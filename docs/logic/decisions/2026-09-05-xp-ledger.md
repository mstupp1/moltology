## Context

Stage was a stored number with no record of how it was earned. That made it easy to drift and impossible to audit.

## Decision

Add `xp_transactions` with a unique source key per member, such as `routine:<task>:<date>`. Awards insert rows and undo deletes them. `syncUserProgression` sums the ledger and writes `xp` and `stage`. Members with an older stage get one legacy row so they keep it.

## Alternatives

- Increment `profiles.xp` in place. Rejected because replays double count and nothing is auditable.

## Consequences

- Stage can only change through earned XP, which enforces the red line in code.
- The ledger trusts the date sent by the client, which is a known gap.
